# Repository Guidelines

This file provides guidance to contributors and coding agents working in this repository.

## Project

Windows-only desktop app "Vietnamese's Ultimate W App" (formerly "Quản lý khởi động" / `quanlykhoidong`). Internal name everywhere in code is **`fomeg-windows-app`**: exe `fomeg-windows-app.exe`, lib `fomeg_windows_app_lib`, MCP `fomeg-windows-app-mcp.exe` and MCP server name `fomeg-windows-app`, data dir `%LOCALAPPDATA%\fomeg-windows-app`, registry backup key `HKCU\Software\fomeg-windows-app\Disabled`, identifier `com.fomeg.windows-app`, env vars `FOMEG_*`. Only the display name is "Vietnamese's Ultimate W App". `core/migrate.rs` moves data from the old names (QuanLyKhoiDong dir, com.quanlykhoidong.app WebView2 profile, old registry key) once at startup, before the webview is created. Never reintroduce the old names. The app is for viewing and toggling everything that auto-starts with Windows (Registry Run/RunOnce/Policy Run, Startup folders, Scheduled Tasks, services, MSIX StartupTasks), plus a Services tab and live per-item RAM. The UI is bilingual: Vietnamese (default) and English, switchable live in Settings → Giao diện → Ngôn ngữ. Comments, log messages and README stay Vietnamese. **Every new user-facing string goes through i18n with BOTH languages** (frontend `t()` + `src/lib/i18n/{vi,en}/<area>.js`; backend `tr!` + `src-tauri/locales/<area>.yml`); see `docs/i18n.md` and run `node scripts/i18n-check.mjs` (at the repository root) before finishing.

The app is at the repository root (Tauri 2 + Svelte 5 + Vite, plain JS): `src/` (Svelte UI), `src-tauri/` (Rust backend, `locales/` for backend strings), `mcp/` (MCP server crate), `docs/`, `scripts/`, `codex/`. Its Rust backend calls Windows APIs directly. `RustWTM/` is a reference project.

## Commands (run at the repository root)

```powershell
npm install
npm run tauri dev          # dev: Vite on :1420 + debug exe (runs WITHOUT admin, so writes fail with "Không đủ quyền")
npm run tauri build        # release exe: src-tauri\target\release\fomeg-windows-app.exe (bundle disabled, no installer)
npm run dev                # UI only in a normal browser, using the mock backend (src/lib/mock.js)
npm run build:mcp          # read-only MCP server: src-tauri\target\release\fomeg-windows-app-mcp.exe (no admin manifest); `npm run tauri build` runs it first and embeds the exe
```

Backend only (inside `src-tauri/`):

```powershell
cargo check
cargo clippy --release
cargo test --release --lib --test scan --test tick -- --nocapture  # unit tests + real scan + full monitor-tick cost on this machine
cargo test --release --test scan exe_path_parsing                 # single test
```

Plain `cargo test --release` fails on the `main.rs` test binary with os error 740 (the release manifest requires elevation); run the `--lib` / `--test` targets as above.

- `build.rs` picks the manifest. Release builds embed `app.manifest` (`requireAdministrator`, so UAC prompts on launch). Debug builds embed `app-dev.manifest` (`asInvoker`). Set `FOMEG_NO_ADMIN=1` to build a release exe without the admin requirement. Both manifests must keep the Common-Controls v6 dependency (Tauri needs it).
- Release uses `panic = "abort"` and `windows_subsystem = "windows"`, so there is no console. Diagnose with `util::log_line` (`%LOCALAPPDATA%\fomeg-windows-app\log.txt`) or by returning `Err(String)` to the UI.

## Tauri architecture

### Backend: `src-tauri/src/`
- `core/scan.rs::run()` runs four scanners in parallel threads: `registry` (Run, RunOnce/Policy, backup key, MSIX), `folders` (Startup folders, `.lnk` via IShellLinkW), `tasks` (Task Scheduler COM, with folders split across worker threads, each with its own `ITaskService`), and `services` (SCM API, with per-service config queried in parallel). It then resolves publishers (version-resource CompanyName) in parallel. Typical full scan is ~0.4 s, dominated by Scheduled Tasks.
- The publisher cache is kept in memory and persisted to `%LOCALAPPDATA%\fomeg-windows-app\pubcache.json`, keyed by lower-cased path and validated by mtime+size.
- **`Item.kind`** decides both how an entry is toggled (`core/actions.rs::toggle`) and how its RAM is matched (`state.rs::matcher`). The meaning of `key1/key2/key3` per kind is documented on the `Item` struct in `core/mod.rs`. The startup list contains `Service` copies of `Svc` entries with the same `key1`; after a service changes, both copies must be updated (the frontend does this, and the backend re-tracks PIDs via `AppState::update_service`).
- Service/start-type values go over the wire as codes (`start_type`: auto|delayed|demand|disabled|boot|system; `state`: running|stopped|starting|stopping|paused|pending). The frontend maps them to Vietnamese labels, so don't send localized strings from Rust.
- `CRITICAL` (in `core/mod.rs`) lists services the backend refuses to set to Manual/Disabled or to stop. Items carry a `critical` flag for the UI.
- Layout: `lib.rs` (setup + handler list), `commands.rs` (every Tauri command), `state.rs` (`AppState`, RAM matchers, 1 h metrics history), `monitor.rs` (the single sampling thread).
- **Monitor thread** (`monitor.rs`): each tick (default 1 s; `set_interval` accepts 500/1000/2000/5000 ms or 0 = paused) calls three samplers:
  - `core/procs.rs::ProcSampler`: one `NtQuerySystemInformation(SystemProcessInformation)` pass gives per-process CPU %, private working set, disk I/O rate, threads and handles. Static info is cached per (PID, create time).
  - `core/metrics.rs::MetricsSampler`: per-core CPU, memory, PDH disks, per-LUID network counters, battery.
  - `core/gpu.rs::GpuSampler`: PDH `GPU Engine(*)` (the same method Task Manager uses) plus GPU memory.
  
  A full tick costs ~5 ms. It emits `ram` (MB per startup/service item, only the changed values) and `metrics` every tick. It emits `procs` only while `set_watch({procs:true})` is on: static info in `added`, numeric `rows`, and `removed`; `reset` means a full list. When the window is hidden or minimized, or updates are paused, it samples every `AppState::idle_ms` (`set_idle_interval`: 5 s default, 15 s, 60 s, or 0 = no samples; it just waits for a wake from `set_visible`/`set_interval`, re-checking at most every 15 s) for history and emits nothing. A wake (after a scan or an action) triggers an immediate sample only while the UI is visible.
- Process actions are in `core/proc_actions.rs`. Kill is an immediate `TerminateProcess` with SeDebugPrivilege (what `taskkill /F` does), children first for a tree kill, and it refuses critical system processes. Restart relaunches a non-elevated target with the shell's token. `core/icons.rs` turns exe icons into cached PNG data URLs.
- **AI chat** (`core/ai.rs`, spec in the "v3" AI section of `docs/contract-v2.md`): three providers, one active at a time, each with its own model, base URL and DPAPI-encrypted key in `%LOCALAPPDATA%\fomeg-windows-app\ai.json`. All calls are raw HTTPS through `ureq` with SSE streaming.
  - `anthropic`: the Messages API with `anthropic-version: 2026-10-21`. Default model `claude-opus-5-5`, effort `medium`. Server-side fallbacks are sent only for models that support them.
  - `openai` and `custom`: OpenAI Chat Completions (`{base}/chat/completions`). `custom` is any OpenAI-compatible endpoint; its base URL is required and its key is optional. `reasoning_content` maps to the `thinking` event. Model names are not hard-coded: the user picks one from `ai_list_models` (`GET {base}/models`).
  - History: provider-neutral turns (text). Anthropic-produced turns also keep their raw content blocks (thinking), which are replayed only to Anthropic, append-only. Thinking from before a fallback boundary is filtered out of the outgoing copy.
  - Tests: `tests/ai_http.rs` drives both wires against a local mock HTTP server. Tests must use a temp config path, never the user's real `ai.json`.
  - Machine snapshot: the optional snapshot (`AppState.context`, built by the monitor) goes in the user turn as a `<system_snapshot>` block, never in the cached system prompt.
- Codex worker prompts and run scripts used to build these modules are in `codex/` (`prompts/`, `run3.sh`).
- **Disk usage page** (`core/du.rs`): TreeSize-like folder sizes, shown live while scanning. Each folder is listed with `GetFileInformationByHandleEx(FileFullDirectoryInfo)` into a 64 KB buffer (sizes, allocation, attributes, times in one call, no per-file opens) by ≤ 6 worker threads (6 measured fastest; more threads contend inside NTFS/Defender) taking work from a shared LIFO. Each folder locks the tree once to record its totals and bubble them up to all ancestors, so `du_children` can read a consistent, growing tree at any time. Only folders are stored (56-byte nodes, first-child/next-sibling links, names in shared 256 KB chunks, nodes in fixed 16k chunks so the tree never reallocates under the lock); "files directly in a folder" = node total − children totals, and the files themselves are listed on demand (`du_files`). Junctions/symlinks are not followed. Measured on this machine: whole C: (2.77 M files, 595 k folders) in ~33 s with a ~45 MB tree; `du_drives` ~1 ms (network drives are detected via `QueryDosDeviceW` and never touched, others answer within 1.5 s).
- **Disk usage × AI**: `Scan::ai_summary` (≤ 4000 chars, ~6 ms) goes to the model as a `<disk_scan>` block through `ai_send`'s `disk` arg, only from the Disk page or "Hỏi trợ lý AI về thư mục này", and is not re-sent in the same chat unless something changed. The model proposes deletions in a fenced `xoa` block (see AI action proposals below). In the junk rules (`JUNK` in `du.rs`) an empty label marks an excluded area (installed programs, global npm packages, WinSxS).
- **Ports page** (`core/ports.rs`): `ports_list` reads the IP Helper tables (listening TCP, bound UDP, established counts) in ~2 ms. Process name/CPU/RAM are NOT sampled again: `ports_list` stores the PIDs in `AppState::port_pids` and the monitor copies only those PIDs' info into `port_procs` each tick, and only while the page asked within 6 s. The UI polls every 2 s only while the page is open, visible and not paused. The known-port catalog and the "don't end this" rules live in `src/lib/ports.js`. `ai_send`'s `ports: true` attaches a backend-built `<ports>` block (≤ 3500 chars).
- **Cleanup page** (`core/cleanup.rs`, Hệ thống → Dọn dẹp): `cleanup_scan` lists fixed locations (user/Windows Temp, WER reports, dumps, Windows Update download, Delivery Optimization, shader caches, INetCache, Recycle Bin) and finds app caches by folder NAME (`CACHE_NAMES`) in AppData and the profile's dot-folders (never Documents/Desktop/projects; skips node_modules, .git, extensions, venvs, LocalCache), grouped per app (`app_label`). Discovery has a 2.5 s budget; sizes are measured with `du::list_dir` on 6 threads with a round-robin per-item queue, so small items finish first. After 0.8 s it returns with the rest `pending`; each finished item arrives as a `cleanup_item { scan, item }` event. `cleanup_apply(id, items, keepRecent)` takes item IDS of the latest scan (never paths) and deletes permanently inside each root (the root is kept): children are opened relative to the parent handle (`NtOpenFile`, `FILE_OPEN_REPARSE_POINT`, backup intent + SeBackup/SeRestore), files with share 0 (files in use are skipped silently), POSIX delete ignoring read-only, junctions/symlinks never followed or removed, optional "keep files changed in the last 24 h". Deleting runs on 6 threads that share one queue of FOLDERS (`Deleter`: a folder keeps its handle only until its children are done, then is removed if empty), so one big Temp folder is split across threads; afterwards only the cleaned items are re-measured and returned (`ApplyOut.items`), no full rescan. The Recycle Bin uses `SHEmptyRecycleBinW` without UI, in parallel. Progress: the delete threads add to a shared `Tally` (atomics, once per folder) and a reporter thread emits `cleanup_progress` every 250 ms while visible; `CleanupProgress.svelte` shows it as one 24 px line (4 px bar moved by `transform`, files, freed bytes, ETA) above the status bar, only on the Cleanup page. Measured here: first scan result ~2 s, everything (incl. a 1.25 M-file uv cache) ~15 s; deleting 20 000 fresh files 5.8 s on 1 thread → 2.9 s on 6 (the per-file cost is the Defender/NTFS filter on open, so more threads or delete-on-close don't help; `bench_delete`). `ai_send`'s `cleanup: true` attaches `<cleanup>` (≤ 3500 chars) from the last scan.
- **Apps page** (`core/apps.rs`, Hệ thống → Ứng dụng, like Windows Settings → Installed apps): `apps_list` reads the `Uninstall` keys (HKLM 64/32-bit + HKCU; filtered like Windows: no `SystemComponent`, `ParentKeyName`, update `ReleaseType`, or entries without an uninstall command) in ~70 ms, plus Store/MSIX main packages of the current user via WinRT `PackageManager` (system-signed packages skipped; display name/logo lookups split over 6 threads, ~0.2–0.4 s). Apps without `InstallLocation` get the folder of their uninstaller/icon (`location_guessed`). Real size = the install folder measured with `du::list_dir` on ≤ 6 threads (`apps_measure(gen, paths)` → `app_size` events, 20 s per folder then a partial "≥" size, cached 10 min, stopped when the page closes); otherwise the installer's `EstimatedSize` (shown as "≈"). Uninstall (`apps_uninstall(id)`, one at a time) re-reads the entry by id and runs the app's OWN uninstaller like Windows (`MsiExec /X{GUID}` for MSI) via `CreateProcessW` suspended inside a Job Object, so NSIS/Inno second-phase copies are tracked too; when the job is empty it checks whether the registry key is gone and emits `app_uninstall { id, name, removed, error }`. Store apps use `RemovePackageAsync`. A non-elevated dev build falls back to `ShellExecuteEx runas` and waits on that process only. UI: `AppsPage.svelte` + `AppInspector.svelte` + `apps.svelte.js`; each row has a Windows-style "…" button (Sửa đổi / Gỡ cài đặt / folder / registry / copy command / AI), the same menu on right-click, and the confirm uses `store.confirm`. "Hỏi AI" relies on the `installed_apps` tool (no context block).
- **Apps / leftovers caching** (fast AND never stale): `apps::list()` keeps the last full read (~0.43 s here) and reuses it while a CHANGE STAMP is unchanged – the last-write times of the 3 `Uninstall` keys + the user's Store package repository key (install/uninstall changes them; reading 4 keys < 1 ms) – and for at most 2 min (in-place version updates). Re-reads hold the lock so concurrent callers share one read. Last-used values are recomputed from the remembered exe names whenever `usage.rs` has a newer read (~1 ms, no disk). Measured: cached `list()` 0.48 ms; `related()` 2–97 ms (only real measuring left), 1 ms when seen before. `leftovers.rs` keeps owners + level-1 folder listings (`Ctx`) for 30 s keyed by `apps::generation()`; folder sizes (with newest mtime) are shared through `apps::cached_walk` / `remember_walk` (10 min); `du_delete_paths` calls `apps::forget_sizes` + `leftovers::invalidate`; uninstall and `apps_list(force)` (Làm mới / F5) drop everything. The UI re-requests the list silently each time the page opens (instant, fresh), coalesces `app_size` events (≤ ~8 redraws/s) and keeps related folders 2 min per app (showing the old result while refreshing). Follow this pattern for new data: cheap change detection + explicit invalidation on our own actions, never a long blind TTL.
- **Last used** (`core/usage.rs`): what Windows already records, read-only, cached 60 s (~5–20 ms): BAM (`SYSTEM\CurrentControlSet\Services\bam\State\UserSettings\<SID>`, `\Device\HarddiskVolumeN\…` paths mapped with `QueryDosDeviceW`, Store family names; admin), Prefetch (`%windir%\Prefetch\NAME.EXE-HASH.pf` mtime by exe name; admin) and UserAssist (HKCU, ROT13 names with KNOWNFOLDERID prefixes, run count + last time). `apps::list` fills `last_used` / `launches` per app (exes of the install folder, level 1–2, on 6 threads; uninstallers/updaters/crash handlers and generic exe names ignored) and `usage_full` (BAM/Prefetch readable). The Apps page shows a "Dùng lần cuối" column and a "Lâu không dùng" tab (> 90 days, or never seen with full data); `installed_apps` (sort `last_used`), `startup_items`, `services`, `service_details` and `process_report` include it, and `SYSTEM_TOOLS` tells the model to weigh it (it is only a hint: background programs count too).
- **Webview hardening / dev robustness** (`src/main.js`): the WebView2 context menu is blocked except in text fields of the release build (app menus still work because components get the event), and F12 / Ctrl+Shift+I/J/C/K / Ctrl+U/P/S are swallowed; in dev hold Alt to keep them. Release builds have no DevTools anyway; secrets stay in Rust (DPAPI) and AI traffic goes from Rust, so this is only about casual inspection. Uncaught JS errors / rejections become an error toast. Every `*.svelte.js` store calls `import.meta.hot.decline()` so editing one reloads the page instead of leaving two instances (old one watched by mounted components) after HMR.
- **Related folders & leftovers** (`core/leftovers.rs`): there is no fixed place, so an app is identified by keys from its name (without version / parentheses / publisher words), install-folder name, icon exe stem and publisher. Only level 1 of AppData Roaming/Local/LocalLow, Local\Programs, ProgramData, Program Files (x86) and the profile's dot-folders is listed (`du::list_dir`, a few ms), plus level 2 inside the publisher's folder. Matching is strict (`key_match`: exact, or a 6+ char key plus digits / ≤ 2 chars) with `STOP`/`NEVER` lists; a folder that also matches ANOTHER installed app (incl. hidden Uninstall entries) is `shared` and never pre-checked. `apps_related(id)` (~0.3 s + measuring ≤ 5 s) feeds the inspector's "Thư mục liên quan" and the uninstall popup: uninstall opens `ActionReview` with kind `go_cai` (rows = install folder + related folders, `allowEmpty`), runs the uninstaller, and only when `app_uninstall.removed` is true moves the checked folders to the Recycle Bin (`du_delete_paths`). Leftovers (`leftovers_scan`, tab "Còn sót lại", ≤ 15 s): `apps_list` remembers the apps it saw (`apps_seen.json`); apps that disappear, or are uninstalled here, go to `apps_removed.json` and their folders are searched (skipping folders an installed app still owns); `AppData\Local\Packages\<family>` without an installed package = orphaned Store data; `WindowsApps` folders not installed for this user are packages of other accounts (removable only via `RemovePackageWithOptionsAsync(RemoveForAllUsers)`, `leftovers_remove_packages`), provisioned, old versions or orphans (report only, `kind: "info"` – never delete TrustedInstaller folders by hand). `leftovers_forget(name)` drops an app from the history.
- **Agent tools** (`core/agent_tools.rs`, plan in `docs/agent-tools-plan.md`): one READ-ONLY `Toolbox` (19 tools: `system_overview`, `hardware`, `metrics_history`, `list_processes`, `process_report`, `process_tree`, `startup_items`, `services`, `service_details`, `ports`, `drives`, `disk_usage`, `scan_folder`, `folder_files`, `cleanup_report`, `installed_apps`, `app_folders`, `leftovers`, `app_info`) shared by the in-app assistant and the MCP server. Each tool = name + English description + JSON schema; results are compact Vietnamese text capped at `MAX_OUT` (6000 chars). It samples processes/metrics/GPU only when a tool asks (two samples 0.5 s apart, reused for 2 s), scans startup/services once per 60 s, and reads app-only data (1 h history, Disk scan, Cleanup scan) through the `AppData` trait (`commands.rs::AppView`). Command lines are passed through `redact`. `scan_folder` measures any folder on demand with `du::Scan` (12 s budget, then partial "≥" sizes; the tree is dropped after the answer), so the assistant never has to ask the user to scan on the Disk page first. **No tool may change the machine**; changes go through the action-proposal blocks below. A new feature with new data gets its tool here (description + schema + a case in `real_tools_run`) in the same change.
- **Tool-use loop** (`ai.rs::Client::stream_response`): sends `tools` (Anthropic `input_schema` / OpenAI `function`), runs requested tools, sends `tool_result` / `role: tool` back, and repeats until a reply without tool calls (≤ `TOOL_ROUNDS` 8 rounds, `TOOL_DEADLINE` 180 s, `TOOL_TRANSCRIPT` 120 k chars; the last round sends `tool_choice: none`). The tool messages of a turn are kept in `HistoryTurn::exchange` and replayed only to the provider that produced them. An OpenAI-compatible server that rejects `tools` (HTTP 400/422 on round 0) gets the turn without tools. UI: `ai` event `{ kind: 'tool', id, name, label, args, phase: start|done, ok, chars }` → "Đang xem / Đã xem …" steps above the reply. Setting: `tools` (on by default, stored as `no_tools`). Test: `tests/ai_http.rs::tool_loop_runs_read_only_tools_and_resends_results_on_both_wires`.
- **MCP server** (`core/mcp.rs`, crate `mcp/` → `fomeg-windows-app-mcp.exe`, `npm run build:mcp`): JSON-RPC 2.0 over stdio (`initialize`, `ping`, `tools/list`, `tools/call`, `prompts/*`), the same Toolbox, read-only, no network listener. It is a separate crate because tauri-build embeds the app's `requireAdministrator` manifest into every binary of `src-tauri`; `fomeg-windows-app-mcp.exe` runs without UAC. One file to ship: `beforeBuildCommand` runs `build:mcp` first, `build.rs` sets cfg `embed_mcp` when `target/release/fomeg-windows-app-mcp.exe` exists, `main.rs` `include_bytes!` it, and on launch the app extracts it to `%LOCALAPPDATA%\fomeg-windows-app\fomeg-windows-app-mcp.exe` (`mcp::install`, only when the bytes differ; a running old copy is renamed to `.old`). While the app is open, `fomeg-windows-app-mcp` forwards each tool call over a named pipe (`core/agent_pipe.rs`: per-session name, DACL = current user + SYSTEM with a Medium label so the non-elevated MCP can reach the elevated app, remote clients rejected, the client accepts only a pipe served by `fomeg-windows-app.exe`), so agents get the app's live data (`AppView`: 1 h history, Disk scan, Cleanup scan); otherwise it samples locally and retries the pipe every 5 s. Only Toolbox tools run over the pipe. The Settings page (Agent tab) shows per-client setup from `mcpClients.js` built on `mcp_info` → `{ path, exists, embedded }`. Test: `agent_pipe::tests::mcp_reaches_the_open_app_through_the_pipe_read_only`.
- **AI action proposals** (shared, `src/lib/aiActions.js` + `reviewKinds.js` + `ActionReview.svelte`): the model writes a fenced block whose language is a registered kind (`xoa` = delete paths, `dong_cong` = end the programs holding ports, `don_dep` = clean Cleanup items by id, `tat_khoi_dong` = disable startup items by name, `dich_vu` = `service: thu_cong|tat_han|tu_dong|tu_dong_tre|dung|chay`, `ket_thuc` = end processes by PID or image name, re-checked with `proc_lookup` and shown ONE ROW PER APP with its exe icon, process count, total RAM and an expandable PID list, never one row per PID), one `target | reason` per line. Review rows may carry `exe` (real app icon via `procs.wantIcons`) and `details` (expandable sub-list). Store actions used by handlers take `{ quiet: true }` and return per-item errors, so the popup reports once. `markdown.js` renders a card. Its button sets `ai.review = { kind, items }`, and the shared popup validates items with the kind's handler, shows per-item checkboxes, "Chọn tất cả" and the kind's options, then runs only the checked items. The model never acts. To add a kind, register it in `aiActions.js`, add a handler in `reviewKinds.js`, and teach the block in `SYSTEM` (`core/ai.rs`).
- `core/shell.rs`: the native Explorer context menu (`IContextMenu` + `TrackPopupMenuEx` on the UI thread via `run_on_main_thread`, with the window subclassed while it's open so "Send to"/"Open with" submenus draw), Recycle-Bin / permanent delete (`SHFileOperationW`), and the folder picker (`IFileOpenDialog`). `du::protected` blocks deleting drive roots and system folders.
- Every command does its work in `spawn_blocking` (service start/stop waits up to ~8 s for the state to settle; bulk service ops run in parallel threads). Nothing blocks the webview.
- The JS ⇄ Rust contract is specified in `docs/contract-v2.md` and wrapped in `src/lib/api.js`. `src/lib/mock.js` + `mock-v2.js` mirror it for browser-only UI work. Keep `commands.rs`/`monitor.rs`, the contract doc, `api.js` and the mocks in sync. Tauri converts command args to camelCase; the AI commands use `rename_all = "snake_case"` (`chat_id`, `api_key`, `include_context`).

### Frontend: `src/`
- **i18n** (`src/lib/i18n.svelte.js`, spec `docs/i18n.md`): self-written (no library: zero deps, no reload on switch). `t(key, params)` reads `i18n.locale` ($state) so templates update live; plurals via Intl.PluralRules (`key_one`/`key_other`); `labels({...})` for code→label tables; numbers/dates via `i18n.intl` / `format.js`. Vietnamese is bundled, English (`i18n/en`, ~76 KB) is loaded on demand; `main.js` awaits `i18n.init()` before mount and tells the backend (`set_locale`). Never put `t()` in a module-level constant (it would not update): use `$derived`, `labels()` or a function. Don't match backend/model text in Vietnamese only (regexes that must read it carry `// i18n-ignore`). Backend: `rust-i18n` YAML (`_version: 2`, `vi`+`en`) through `tr!` (`core/i18n.rs`, default vi also in tests/MCP); UI-facing errors/labels are translated, model-facing text (agent tools, MCP, AI prompts) is not; when the UI is English `ai.rs` appends `REPLY_EN` so the assistant answers in English. Some backend labels are produced at scan time and switch language on the next scan.
- Svelte 5 runes. Stores: `store.svelte.js` (startup/services), `sys.svelte.js` (metrics + history), `procs.svelte.js` (plain `Map` by pid plus a version counter; apply `removed` before `added`), `ai.svelte.js`, `prefs.svelte.js`, `cleanup.svelte.js` (Cleanup page data, kept across page switches). Tables are self-written virtual lists (`DataTable.svelte`). Charts are one self-written canvas component (`Chart.svelte`) that redraws only on new data. Icons come from the Windows icon font (Segoe Fluent Icons) via `Glyph.svelte`. No chart or UI libraries, to keep WebView RAM and CPU low. Don't add heavy dependencies.
- **Table + inspector pages** (Processes, Startup, Services, Cleanup) share one layout: `InspState` (`inspector.svelte.js`: width, show/hide and overlay, remembered per page key) + `SplitView.svelte` (resizable right pane, overlay when the page is too narrow) + `InspectorShell.svelte` (kicker, icon, title, sub, actions, body). `ProcInspector.svelte` (processes), `ItemInspector.svelte` (startup/service items) and `CleanupInspector.svelte` fill the shell. Nothing or several rows selected shows an overview; exactly one row shows details. Per-process history is a fixed `Float32Array` ring (`HN` samples) per pid in `procs.svelte.js` (`procs.history(pids)`), so ticks allocate nothing.
- AI replies are rendered by `markdown.js` (own GFM subset: tables, nested lists, task lists, quotes, code). It escapes HTML first, and links render as text, never `<a>`, so the webview can't navigate away.
- Sorting by RAM uses a snapshot taken on sort change, scan, or refresh, so rows don't jump while RAM values update live.

## Design system (must follow)

The current pages (Processes, Startup, Services, Ports, Cleanup) are the reference: compact, dense, calm, like RustWTM / Task Manager. A new page or feature must look and behave the same, built from the shared pieces below. If a piece is almost right, extend it with an optional prop (as `DataTable` got `onfocus`/`ontoggle`) instead of copying it. If two pages grow the same markup or logic, move it into a shared component or module.

### Page anatomy (top to bottom)
1. **Page head** `header.page-head`: `h1` + ONE muted line, then `.ph-actions` on the right (nowrap). The muted line is a summary: plain text, or `.ports-sum` with `<b>` numbers separated by `.dot-sep` (`|`); warnings use `.warn-text`. Actions, in this order: small timing (`.faint.small`, e.g. "1.8 s"), "Hỏi AI" (`Glyph chat`), the inspector toggle (`insp.fits` only, `pane`/`paneClose`), refresh / re-scan as `RefreshButton` (timing goes in its `info`), then at most one primary or danger action (`btn danger solid`). Refresh is never `primary`.
2. **Filter bar** `.toolbar.wtm-bar`: `SearchBox` (280 px) + `FilterTabs` (underlined tabs with counts; `[id, text, count]`) + `span.grow` + `label.check` checkboxes on the right.
3. **Optional chips** `.chips.src-chips` with a label `span.chips-lbl` ("Nguồn:", "Khởi động:"). Chips have counts and toggle on click. When a non-default filter is on, offer a way back ("Mọi nguồn", "Về mặc định").
4. **Count line** `p.muted.small.count-line`: "N mục · …". Short status goes here (e.g. "đang đo 2 mục…" with `span.spin.xs`, admin hints in `.warn-text`).
5. **Table**: `DataTable` fills the rest. Cards (`.card`, e.g. the Ports tools card) go above the table only when they are the page's main tool.

### Tables
- `DataTable` with `selection` (a `SvelteSet`): click = select one row (the inspector shows it), Ctrl/Shift-click or the checkbox column = multi-select, double-click/Enter = `insp.open()`, right-click = `onmenu(e, row)`. Arrows, PgUp/PgDn, Home/End, Space, Ctrl+A, Esc work.
- Without `selection` the table is read-only. It still has a focused row: `onfocus(id)` drives the inspector, and Space calls `ontoggle(row)`.
- **Every row checkbox is DataTable's own check column, never a checkbox drawn inside a `cell` snippet.** When the tick means something other than "selected" (Cleanup's "will clean"), pass `checked` (a reactive Set of ids) + `oncheck(ids, on)` (+ `canCheck(row)`, `checkLabel`) to a read-only table. Both modes behave the same: header box = all visible rows, click a box = toggle one, Shift+click a box or row = the whole range from the last clicked/focused row, Ctrl+click = toggle one, Space = toggle the focused row, checked rows are highlighted. Any other list of checkboxes (e.g. the `ActionReview` popup) must also support Shift+click ranges. Don't `preventDefault` a checkbox click to "control" it: the browser flips the box back after Svelte has drawn it.
- Row height 30–32 px, one line per row, text ellipsized with a `title` tooltip. Numbers right-aligned in `.mono`. Size columns: a thin `.res-bar` + value (`.size-cell`). Status: a small pill (`.pill`, `.safety.ok/.warn`), not colored text blocks.
- Don't put several buttons in a row. Row actions live in the inspector and the context menu. If a fixed action column is really needed (Ports tools card), use `.act-slots` so missing buttons keep their space and columns stay aligned.
- Unknown / still-loading values show `đang đo…` / `–` in `.faint`, never 0. Loading tables use the built-in skeleton (`loading`).
- `BulkBar` shows only for ≥ 2 selected. A single selection acts through the inspector.

### Settings page
- Like RustWTM's Settings: page head (the muted line describes the current category), then the category bar (`FilterTabs` without counts in `.toolbar.wtm-bar`, last category remembered as `ui:settingsTab`), then a scrolling `.set-body` with one full-width column (`.set-col`, fills whatever the sidebar and AI panel leave) of `h2.opt-group` headings + `OptionRow`s. Categories: Giao diện, Cập nhật & hiệu năng, Các trang (per-page prefs: Startup default sources `ui:startupAll`, `proc:noAskKill`, Apps `ui:staleDays`), Trợ lý AI, Agent (MCP), Windows, Phím tắt, Thông tin (version, log, data folder, full machine specs from `system_info` incl. SMBIOS model/BIOS, with "copy all"). A new setting goes into the matching category as an `OptionRow`; a new keyboard shortcut goes into `KEYS` in `SettingsPage.svelte`. Lists that are not options (shortcuts, machine info) use `.opt-card`.
- **Every row is a real option** (a switch, select, segmented control or action button that does something). Never add an info-only row that looks like a setting. A planned option that is not built yet is an `OptionRow` with `soon` ("Sắp có" badge, its control disabled); build it later instead of leaving text. A safety rule that must not be turned off is shown as a locked switch (`on disabled`) with the reason in `desc`.
- MCP setup: `mcpClients.js` lists each AI client (Claude Code, Claude Desktop, Codex, Antigravity, Gemini CLI, Cursor, VS Code, Windsurf) with steps, its config file and generated command/JSON/TOML; the user picks one in a select. Snippets always use `mcp_info().path` (release: the current user's `%LOCALAPPDATA%\fomeg-windows-app\fomeg-windows-app-mcp.exe`), never a hard-coded path. Add a client there, not in the page.

### Inspector (right pane)
- Always `InspectorShell`: kicker, icon (`exeIcon` image, else `NavIcon`/`Glyph`), title, `sub` (`span`s separated by `·`), `actions` (controls first, then `.insp-act-break`, then `btn sm` buttons, the AI button as `icon-only`), then the body.
- Body order: one `.insp-card` with `.ic-stats` (2 big numbers) and optionally a `Chart` → a short explanation `p.small` → warnings `p.note.warn` → `.insp-card.res` sections (`.res-head` with a Glyph + bold title + `.res-val`, `.res-row`s, thin `.res-bar`s) → `dl.props.insp-props` → `.cmd-block` for paths/commands (copy button).
- Nothing focused (or several selected) shows an **overview**: `accent` icon, `.insp-counts` (3 numbers), breakdown bars, a "largest / heaviest" list whose rows (`.res-row.link-row`) select that item, and one `.faint.small` hint line.
- Startup and service items show only RAM (live value + chart sampled only while shown, 1/s, ≤ 120 points, paused when hidden), with no CPU/GPU/disk, because the app tracks only RAM for them (`state.rs::matcher`). Link to Processes (`procs.revealPid`) for full metrics. Processes show CPU/RAM/disk/GPU.

### Look and density
- Colors only from the CSS variables in `app.css` (`--bg`, `--panel*`, `--border*`, `--text`, `--muted`, `--faint`, `--accent`, `--green/--orange/--red` + `-soft`). Data colors from `colors.js` (`C.cpu`, `C.mem`, `C.disk`, `C.gpu`…). No hard-coded hex in components; both themes must work.
- Type: 13 px base, 12–12.5 px in tables, 11.5 px for labels and secondary text, 17 px for big numbers (`font-variant-numeric: tabular-nums`), `--mono` for paths, PIDs, ports, sizes in tables. Bold (600) only for titles and key numbers.
- Spacing: 6–10 px gaps, 8 px radius for cards, 6 px for inputs. Buttons: `btn` (30 px), `btn sm`, `btn xs`, `icon-only`. Inputs: `.input` / `.input.sm`.
- Green = good / safe / running, orange = caution, red = danger / destructive. Destructive buttons are `btn danger` (`solid` only for the page's main action) and always go through `store.confirm` or `ActionReview`.
- No continuous animations (only spinners while loading). No new icon or UI libraries.

### Behaviour
- Text is short and plain, written in Vietnamese with an English counterpart (i18n). Say what will happen ("Dọn = xoá vĩnh viễn…") and what is skipped.
- Long work (scans, deletes) never blocks the UI. Show partial results early and stream the rest (Disk page tree, Cleanup `pending` items via events). Keep page data in a module store (`*.svelte.js`) so switching pages doesn't rescan.
- Page-specific AI: a "Hỏi AI" button in the head (`ai.askX()`, sends a backend-built context block, not re-sent unchanged), page suggestions in `AiPanel` (`pageHelp`), and action proposals through the shared `ActionReview` popup. The AI never acts by itself.
- Startup default filter: sources default to Registry Run + Startup folder (`DEFAULT_KINDS` in `store.svelte.js`) on every launch. Opening an item from elsewhere (`store.reveal(list, id)`) widens the filters so the item is visible.
- Icons: page/menu icons are RustWTM's line icons (`NavIcon.svelte`, exact coordinates from `RustWTM/crates/wtm-gui/src/navigation.rs`: 19×19, 1.6 px stroke). Use `NavIcon` wherever a page is represented (sidebar, inspector title, overview).

### Performance
- Nothing polls or samples unless its page or panel is visible. Hidden/minimized/paused means no work. Prefer reusing the monitor's existing sample (or an existing scanner such as `du::list_dir`) over new system calls.
- Effects that write state must `untrack` the writes, or they loop (`effect_update_depth_exceeded`). Use `$state.raw` / plain Maps + a version counter for big lists.
- Filesystem walks: `du::list_dir` (one call per folder, no per-file opens), ≤ 6 threads, never follow junctions/symlinks, and put a time budget on anything that can be unbounded.

### Editing
- **Text with backslashes** (Windows paths, regex, `\n` in JS/Rust/Markdown): edit with the Edit tool, not shell heredocs or Python scripts, which collapse `\\`. Several source files use CRLF line endings; scripts that patch files must keep them.
- Preview UI changes on the mock (`npm run dev`, :1420) and keep `mock.js` / `mock-v2.js` in sync with new commands.
